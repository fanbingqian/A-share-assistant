结论先行（TL;DR）

01 · 要不要智能体入驻

要「受限编排层」，不要「常驻通用助理」

OpenClaw / Hermes / Goose 这类个人助理权限面太大、行为不可审计，不适合接进一个已有判断链路的投研系统。需要的只是一个可一键关闭、只读事实账本、只写提案的薄层。

02 · 选哪个

首选 Node 原生薄适配器；LangGraph 留作第二阶段 sidecar

现有系统是 Node 零第三方依赖的单服务。首选不引入任何框架，用内置 fetch 调 OpenAI-compatible 接口跑 3 个纯任务；确需多角色长流程时，再上 LangGraph（MIT）作为独立 Python sidecar。

03 · 三大需求现状

不是「没做」，是「闭环没走通」

自动选股与实时监控已有真实代码；经验库五段式已建，但 rules.json count=0、4 条经验全 pending、样本 18/30。先把闭环跑通，比重建一套系统重要得多。

二、智能体选型：要不要入驻，选哪个

2.1 结论

需要「编排」，不需要「驻场助理」。选股与监控是确定性、可回测、可归因的计算任务，必须由规则与因子引擎完成；LLM 不可复现、无法回测、无法审计，让它参与打分会把「不出现幻觉」这条铁律直接破掉。LLM 在这个系统里只配做三件事：把用户的话分类、把已发生的事实写成复盘草稿、把术语说成人话。

更要紧的是栈的匹配：现有后端是 Node 内置模块、零第三方依赖、无 package.json、8777 单服务。上一轮清单里最主流的 LangGraph / CrewAI / Pydantic AI 都是 Python，直接引入就要维护第二套运行时、进程间通信与部署边界，对一个已经跑稳的系统是净负担。

2.3 LLM 只做三个「纯任务」，产出都是提案

任务输入（只读）输出（结构化，先入待审）
分诊 Triage用户一句自然语言{intent: add_factor|add_experience|query_pool|review_ask, confidence, need_clarify}；低置信度进「待澄清」，不猜。

确定性网关（永远加载，不依赖 LLM）四道校验：
  1. 事实账本核对：每个数字 / 日期 / 事件必须挂 factId，查不到即剔除并标注；
  2. schema 校验：缺字段、越界、不可计算 → 直接拒绝；
  3. 幂等去重：同主题同日不重复入队；
  4. 一律落「待审队列」，绝不直接写生效态。
这四道正是你 11-18 设计文档 §2 的「一道闸」，此处把它固定成永远加载的独立模块 server/agent-gate.js。

4.1 股池：双来源 + 入池闸门

pool_item {

  source: 'manual' | 'screened',          // 自己选的 / 从每日选股结果选的

七、合规与反幻觉边界

  • 不自动下达委托单：证监会《证券市场程序化交易管理规定（试行）》把程序化交易定义为「通过计算机程序自动生成或者下达交易指令」，自 2024-10-08 施行；按此定义，回测、信号展示、人工按信号下单、券商 APP 条件单均不落入该定义。一旦脚本自动发单，即须「先报告、后交易」，报告内容含交易策略类型、最高申报速率、单日最高申报笔数、软件名称及版本号（第七条）。报备通道为券商会员端，个人无直报入口。来源：中国证监会官网 csrc.gov.cn 发布稿与规定原文 PDF，2024-05-15 发布 / 2024-10-08 施行，一手；报备流程细节来自券商公开答疑 2026-10-27，非一手，需核实。
