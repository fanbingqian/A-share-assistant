AI-Hel2 知识库评估 · 消息转知识库逻辑设计 · 图谱分布方案

2026-11-21 · 面向 A 股智能系统 v2 个人知识库模块 · 含 GitHub / 论文调研结论
一句话结论：AI-Hel2 的设计思想值得借鉴，但整套系统不适合直接移植。它的价值在于「Agent 只存不提取」「置信度 + 去重 + 反馈闭环 + 衰减」这套工程方法；但它实际落库只有 22 个实体、17 条关系，合成/本体/反馈/待合并四张表全部为空，且内容是旅行规划而非金融，图谱引擎与 Tauri/Rust/Python/Heimdall 深度耦合。建议：只借鉴规则与设计，在当前零依赖 Node 服务里增量实现，不要搬它的运行栈。

一、AI-Hel2 知识库评估

1.1 它实际是什么

维度实际情况判断
前端Tauri + React + Zustand，图谱用 SVG + d3 力导向（phase4 PixiJS 只是规划文档）渲染层已移植到本项目 graph-engine.js，无需再动
存储SQLite knowledge_cache.db：cache_entities / cache_relations + 迁移 002 的 5 张新表；不是 Neo4j，Heimdall 只是基于这两张表构建内存图索引结构可映射到本项目的 graph.json，规模小无需图数据库
提取extract_service.py 异步轮询 → 调 LLM → 输出实体/关系 JSON → 回写；Agent 只调 nexus_store(raw_text)「只存不提取」职责分离是最大可借鉴点
数据来源source_type 枚举：chat / wikilink / wiki / canvas / upload_doc / upload_image / agent_memory / synthesis可直接复用分类思想，映射到本项目消息源
实际数据量实体 22，关系 17，内容索引 14；合成 0、本体 0、反馈 0、待合并 0高级能力停留在设计文档，未真正跑起来
实际实体类型location(6)、organization(3)、information_entity(3)、natural_feature(2)、flight_route_status(2)、travel_plan(1)……旅行/航班内容，金融领域完全不适用
实际关系类型located_in(8)、contains(5)、depends_on(3)、depicts(1)缺少金融因果/证据/冲突关系

1.2 可复用 vs 必须重写

能力AI-Hel2 做法处置
标准入库接口Agent 只传原始文本 + source_type + 上下文，提取逻辑集中在服务端借鉴新增 /api/v2/knowledge/ingest，对话/笔记/事件统一走它
提取 prompt角色=知识筛选器；置信度锚点 0.9/0.7/0.5/0.3；宁少勿滥借鉴改写为金融版，保留锚点 + 禁买卖建议
入库过滤confidence<0.4 丢弃；停用词；长度 2–60；编辑相似度 >85% 合并、60–85% 进待确认借鉴直接移植到 dedupe()
多源确认同一实体被 ≥2 类不同来源提取 → 置信度 +0.1（上限 0.95）借鉴本项目的 chat/event/journal 正好构成多源
反馈闭环隐藏 −0.3 / 删除 −0.5 / 聚焦 +0.1 / 提升 +0.3；每 15 条注入偏好摘要借鉴但只注入抽取偏好，不碰 BASE_SYSTEM 买卖纪律
衰减清理孤立 + 低置信 + 7 天 → 隐藏；隐藏 30 天 → 物理删除借鉴防止图谱膨胀
知识合成共享邻居 / 跨文档共现 / 类型模式 → inferred 灰色虚线边简化借鉴本项目同向边已合并；合成边先只做「共现」一种
时序有效性AI-Hel2 无时序建模，事实只覆盖不保留历史缺口必须补：投资逻辑会失效，需 valid_from / valid_to
运行栈Tauri / Rust invoke / Python 提取服务 / Heimdall / SQLite WAL不移植与零依赖 Node 8777 冲突，部署成本高
关键判断：API-Hel2 的实体模型（confidence、importance、namespace、community_id、feedback_score、hidden、inferred）字段设计成熟，但对本项目的 graph.json 而言，一次性铺开全部字段会让抽取和 UI 都变复杂。建议分两步：先补 confidence / sourceType / sourceMessageId / validFrom / status 五个必要字段，跑通链路后再加 feedback_score 与 community_id。

二、网上与 GitHub 调研结果

2.1 对话/消息 → 知识图谱（通用记忆层）

项目 / 论文核心方法对本项目的启发
kg-gen / KGGen
Stanford，MIT/Apache，pip 可装		任意文本或 messages 数组 → 实体/边/三元组；chunking + clustering；做实体与边的聚类去重；经 LiteLLM 支持 DeepSeek；DSPy 结构化输出；自带 MINE 基准最轻的参考实现。它的「实体聚类」「边聚类」正是本项目同向边合并的升级版，可直接读源码借鉴 prompt
Graphiti / Zep
开源框架 + 企业产品		Episode 作为原始锚点；实体/事实/社区；双时序：每条事实有 valid window，变化时旧事实失效而非删除；混合检索 = 语义 + BM25 + 图遍历；支持自定义 Pydantic 本体「事实失效不删除」是解决投资逻辑过期的关键。需 Neo4j/FalkorDB，本项目只借思想不引依赖
Mem0 / Mem0g选择性抽取：不是每句话都入库；记忆整合（合并重叠、衰减无关）；user/session/agent 三级作用域；LOCOMO 基准，token 降 93%证明「宁少勿滥」是对的。本项目的价值门控应照此设计，避免把每日闲聊灌进图谱
PROM
2025 论文 + GitHub		从自然对话构建个人知识图谱；LLM few-shot 三元组抽取；多策略知识融合与冲突消解；修正模块 + 多维评估知识融合与冲突修正的思路可参考；但 Django+Neo4j+Redis 太重
eventual
milesgray/eventual		事件驱动超图：概念为节点、事件为超边（一条边连多个概念），专为聊天场景的态势感知设计；短期/长期记忆分层超图思想贴合本项目的「事件归因」：一个事件同时影响多个概念与个股，比二元边更自然
knowledge-graph-agent
rohanprichard，DeepSeek		DeepSeek + instructor 结构化输出 + Pydantic 模型 + pyvis 可视化；对话中增量维护用户 KG技术栈与本项目最接近（DeepSeek），prompt 与数据模型可直接参考

2.2 金融领域知识图谱

项目 / 论文关键数据与方法对本项目的启发
FinDKG
arXiv:2407.10909		约 40 万篇 WSJ 新闻；时序四元组（实体、类别、关系、时间戳）；15 种金融关系类型；Sentence-BERT 做实体消歧；ICKG 模型抽取「实体 + 类别 + 关系 + 时间」的五元组结构，正是本项目图谱字段设计的参照
FinKario
2025-08		事件增强金融 KG：30.5 万实体 / 9625 三元组 / 19 种关系；两阶段 RAG 取子图；股价趋势预测较金融 LLM 提升 18.81%证明「图谱 + 子图检索」能降低幻觉、提升判断质量；对应本项目的「问答带图谱上下文」
FinKG-News
arXiv:2607.01023，开源		354 个策展事件 → 12407 家公司；80418 实体 / 261168 三元组；事件检测 micro-F1 0.72；置信度 ≥0.9 才保留；事件列表分块 N=20「以事件为锚点」+「高置信阈值」+「证据溯源」是降低金融幻觉的三件套；论文也明确指出：自动幻觉检测不可靠，专家判断不可替代 —— 与本项目的人工闸门一致
调研共识：① 选择性抽取优于全量存储；② 事实要带时间、失效而非删除；③ 所有结论可溯源到原始消息；④ 人工审核闸门不可省；⑤ 图谱用于「召回证据」而非「直接生成结论」。这五条直接构成下面的设计原则。

三、消息转知识库的逻辑设计

3.1 消息源盘点与接入方式

来源当前落盘情况接入设计
对话消息未落盘：前端只保留最近 12 条 history，服务端不存在 /api/v2/chat 追加写入 messages.jsonl，一问一答算一条 exchange
用户笔记notes.jsonl 已 append-only 落盘addNote() 时同步写一条 message 记录，保持单一原始流
事件 / 新闻events-cache.json、stock-news-cache.json只纳入「有标的 + 有影响关键词」的条目，先入候选队列，不自动进图谱
复盘经验data/journal/、ic-lessons.md复用既有审核闸门，抽取后状态置 proposed，人工确认才 active

3.2 四阶段流水线（对应上方图示）

阶段规则产出
① 采集 Ingest所有来源统一写 data/knowledge/messages.jsonl，字段：messageId / source / role / content / symbols / timestamp / contentHash / status；hash 相同跳过append-only 原始流，永不覆盖
② 门控 Gate价值分 = 经验信号词 + 具体标的代码 + 因果词 + 数据/时间 + 问答完整性 − 寒暄/格式词；低于阈值不抽取；用户显式「保存到知识库」直接放行status=candidate
③ 抽取 ExtractHermes 输出固定 JSON：节点（type 白名单 6 类、confidence 锚点）+ 边（type 白名单 5 类）；每节点必带 sourceMessageId；失败回退 extractHeuristic()候选三元组
④ 对齐 Align别名表归一（缩量/缩量下跌）→ 编辑相似度 >85% 同类型合并（保留最旧、合并来源、取最高置信）→ 60–85% 进 pending-merge.json → 名称长度 2–60 → conf<0.4 丢弃去重后的节点/边
⑤ 审核 Review新经验/新因子 = proposed，人工确认才生效；contradicts 边挂到冲突清单，不自动消解人工闸门
⑥ 写盘 Write原子写 graph.json；若新事实与旧事实同主语同关系但冲突 → 旧事实置 validTo 而非删除可回溯、有时效的图谱
⑦ 回流 Feedback问答命中的节点置信度 +0.05（上限 0.95）；隐藏/删除/提升记反馈；每 15 条反馈改写抽取 prompt 的「保留偏好」段；孤立低质节点 7 天隐藏、30 天清理越用越准，但不改交易纪律

3.3 抽取 prompt 要点（金融版）

角色：知识筛选器（不是投资顾问）
任务：从消息中抽取值得长期保存的知识三元组
输出 JSON：nodes[{id,type:concept|factor|experience|pattern|event|question,label,confidence}]
          edges[{from,to,type:supports|contradicts|causes|relates|instance_of}]
硬约束：
 1. 至少 1 个 experience/question 节点，概念+因子 2–6 个
 2. 边必须引用已定义 id；禁止孤立节点超过总数 30%
 3. 禁止任何买卖建议、目标价、仓位指令
 4. 置信度锚点：核心概念 0.9 / 明确定义 0.7 / 有信息量 0.5 / 边缘提及不输出
 5. 无长期价值（寒暄、临时指代、纯格式）→ 输出空 nodes/edges
上下文：附带最近 N 条对话消息用于消歧（借鉴 nexus_store 的 context）

3.4 与低幻觉四层约束的衔接

不可触碰的红线：知识回流只允许影响「抽取偏好」与「召回证据」，绝不写回 L1 BASE_SYSTEM 的金融纪律、L2 的 11 个买卖词硬拦截、L3 bridge GUARDRAIL、L4 Hermes SOUL 人格。经验节点即使被确认，也只是「可被检索的历史判断」，不是「可自动执行的新规则」——沿用 journal 的审核闸门与 hypotheses 的 proposed 状态。

4.2 目标分布（稳定运行 1–3 个月、约 150–300 节点时）

比例来自本项目的知识结构设计 + FinDKG 的实体类别思想，结合「宁少勿滥」调整：

类型目标占比角色定位典型节点

4.3 边与拓扑分布目标

指标目标说明
边类型占比relates 35% / supports 25% / causes 20% / instance_of 12% / contradicts 8%contradicts 保留但单独可视化，不参与自动推理

五、落地路线（建议）

阶段内容依赖
P0 数据补洞清理重复笔记；扩展 graph.json 字段（confidence/sourceType/sourceMessageId/validFrom/status）；新增 messages.jsonl 落盘无
P1 抽取链路价值门控 + 金融版抽取 prompt + Hermes 调用 + 启发式兜底 + 来源溯源P0
P2 对齐审核别名表 + 相似度合并 + pending-merge + 冲突清单 + 人工确认 UIP1
P3 时序与回流valid_to 事实失效 + 问答命中反馈 + 偏好摘要注入 + 衰减清理P2
P4 图谱增强社区着色 + 自适应阈值 + 语义缩放（复用已移植引擎，不动渲染核心）P2
P5 事件锚定对接「日程与事件」模块，事件作为锚点连接个股/概念/因子P3
范围提醒：本方案只做设计与评估，暂不改动现有代码。上一阶段已完成的图谱渲染移植（web/v2/graph-engine.js）保持不变，Hermes 四层约束保持不变。确认方案后再按 P0→P5 逐步实施。
